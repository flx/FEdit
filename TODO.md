## Bugs


- [ ] (find-bar-narrow-column) The find bar cannot compress, so in a narrow editor column its background and hairline spill past both column edges — found by `adv-review-behavior` while reviewing (find-bar-gutter-inset), 2026-08-22, and **pre-existing: it is not caused by that item, which only made it reachable at more widths.** Mechanism, verified in source: every control in `FindBar`'s `HStack(spacing: 8)` carries a hard floor — `TextField(...).frame(minWidth: 120, idealWidth: 220, maxWidth: 260)`, `Text(workspace.findCountLabel).frame(minWidth: 90, alignment: .leading)`, a `Toggle` and a `Button` at intrinsic width — and the only flexible element is `Spacer(minLength: 0)`, which bottoms out at 0. Below a threshold the stack reports a size **larger** than its proposal, and `ContentView`'s `editorColumn.frame(width: editorWidth)` **centres rather than clips** an oversized child, so the padding → `.background` → `.overlay` chain is sized off that oversized frame and the bar's window-background fill *and its bottom hairline* extend past both column edges, over the split dividers; Done also stops sitting 8 pt from the column's right edge. Reviewer's arithmetic, measured off `plans/find-bar-gutter-inset-repro.png` (2×, editor column 508 pt): field bezel 227 pt, toggle 93 pt, count label 90 pt, Done 47.5 pt, 4 × 8 pt spacing = 32 pt, which closes to the pixel against the 508 pt column. Hard minimum content = 120 + 93 + 90 + 47.5 + 32 = **382.5 pt**, so a **≈ 398.5 pt** minimum column once the 16 pt of horizontal padding is added. **That threshold is already exceeded by the default window**: `LayoutMetrics.defaultWindowWidth = 1100`, `defaultSidebarWidth = 1100/3 ≈ 366.7`, and the editor/preview split defaults to half the remainder, giving a default editor column of ≈ 365 pt — so a default-sized window showing a Markdown file has the bar overflowing by ~33 pt before any gutter inset exists. (find-bar-gutter-inset) then adds `gutterWidth` to the requirement: ~20 pt for a short file at the default font size, and ceil(6 × ~16.4) + 8 ≈ **107 pt** for a 6-digit document at `EditorMetrics.maxFontSize = 32`, where the field is also crushed from its 220 pt ideal to its 120 pt floor (~12 visible characters of query). **Not probe-confirmed:** the *rendering* of the overflow — centred spill versus clip — is reasoned from SwiftUI's `.frame(width:)` semantics, not observed; the first tier of the plan must reproduce it and photograph or rasterise the spill before choosing a fix, because if SwiftUI does clip here the item is only about the crushed field and is much smaller. The plan must settle **how the bar degrades**, which is a product choice with several defensible answers and no obvious default: drop the count label's 90 pt floor (it is a fixed width precisely so the controls beside it do not shuffle as the label goes `""` → `1 of 17` → `Not found`, so shrinking it re-introduces that jitter); let the checkbox become icon-only or drop its label; give the field a lower floor; or keep the floors and `.clipped()` the bar so the spill is contained even when the controls do not fit. Note the sibling constraint: whatever is chosen must keep the bar's leading edge aligned with the header strip's title, since that alignment is what (find-bar-gutter-inset) shipped. Cosmetic/layout only; no behaviour change and no SPEC change (§6.5 specifies the bar's controls, not its metrics). `Views/FindBar.swift`, possibly `Views/ContentView.swift`. Depends on (find-bar-gutter-inset), which shipped.

- [ ] (gutter-top-overflow) The line-number gutter draws the topmost partially-scrolled line's number above the editor's top edge, where there is no text row to match it — reported 2026-08-22 with a screenshot: `plans/gutter-top-overflow-repro.png` (scrolled so line 137 is only slivered at the top, its `137` is painted straddling the boundary the editor shares with the chrome above it, i.e. across `ColumnHeaderBar`'s bottom hairline). Two candidate mechanisms the plan must separate, because they take different fixes and the wrong one is a regression: (a) the number is merely flush against the extreme top edge and is being clipped, which is what Xcode does too — then the fix is cosmetic (clamp the drawn `y` into the visible band, or skip a fragment less than ~half visible) and must be justified against the fact that a partially clipped top number is normal editor behavior; (b) the ruler genuinely paints **outside** the scroll view's content area, in which case the fix is clipping/geometry on the `NSRulerView` side, not the drawing loop. Measure the repro against `LayoutMetrics.columnHeaderHeight = 28` to tell them apart. Related-by-boundary, not by cause: the gutter deliberately has no vertical separator line (documented in `drawHashMarksAndLabels` — its top met the header strip and read as a hairline running up through the title), so this is the second cosmetic collision at that same top boundary; keep the two consistent. `Editor/LineNumberRulerView.swift`, possibly `Editor/CodeEditorView.swift` if the fix is ruler geometry, SPEC §6.2.
