- [ ] (find-bar-narrow-redesign) The find bar still overflows a genuinely narrow editor column, and no floor-lowering can fix it — the remainder of (find-bar-narrow-column), which shipped the part that was mechanical and stopped where a product decision starts. **All numbers below are measured, by rendering the real `FindBar` at 2 pt steps and counting ink outside its own frame** (`scripts/FindBarWidthTests` is the harness; the method and its traps are in its header). Current state: the bar overflows at and below **`338 pt + gutterInset`** of editor column, improved from `398 pt + inset`. FEdit's real default editor column is **361.7 pt** — `ContentView` computes `contentWidth = width − sidebar − dividerHitWidth − (isMarkdown ? dividerHitWidth : 0)` and then halves it, so both 5 pt hit widths come off before the split — which means a 2-digit-line-count file (gutter 21 pt) now fits and a **3-digit one (gutter 25 pt) still overflows by about 1 pt**. That last point is cosmetic. What is not cosmetic: **narrow columns are reachable without dragging anything unusual.** At the window's own 700 pt minimum (`FEditApp.swift`) with an otherwise default layout the editor column is **161.7 pt**; dragging the editor/preview divider to `editorFractionMin = 0.15` at a default window gives **108.5 pt**; a 700 pt window with the sidebar at `sidebarMax = 600` gives **13.5 pt**. At 161.7 pt with a 3-digit gutter the bar needs ~363 pt, so it spills ~100 pt past each side — the filed symptom at full strength. **Why the cheap levers are gone:** the query field's floor is already at 60 (it was the only control whose minimum had no rationale); the count readout's 90 pt is load-bearing, because its widest real value `20000 of 20000+` measures **100.7 pt** at `.system(size: 12)`, so that floor is if anything already too small and shrinking it reintroduces the control-shuffling it exists to prevent; and the **Case sensitive** checkbox is now deliberately pinned with `.fixedSize`, because letting it flex is what made the bar silently wrap to two lines (measured heights 31 → 38 → 52 → 94 pt at 600 → 360 → 330 → 260 pt) and then truncate to "Case / sensi…". So the remaining fix has to *change the design*, not tune a number. Options, each defensible and materially different — the plan must pick one rather than assume: (1) **a second row** below a threshold width, moving the count readout and Done onto their own line, which costs vertical space in exactly the windows that have least of it; (2) **an icon-only checkbox** below a threshold, with the label as a tooltip — note SPEC §6.5 says "a visible **Case sensitive** checkbox", so this needs a SPEC sentence, not just code; (3) **drop the count readout into the query field** as a trailing accessory, the way Xcode and Safari do, freeing ~98 pt in one move and arguably improving the full-width layout too; (4) **let the bar scroll horizontally** below the threshold, which keeps every control reachable but hides some of them. Whatever is chosen must keep the leading edge aligned with the header strip's title, which is what (find-bar-gutter-inset) shipped, and must keep the checkbox from wrapping. **Also worth fixing while in here, found by the same review:** the count readout's `minWidth: 90` is smaller than its own widest value (100.7 pt), so the controls DO shuffle when a search caps at `FindMetrics.matchLimit` — pre-existing, cosmetic, and cheap to correct once someone is editing these metrics. Extend `scripts/FindBarWidthTests` rather than writing a new harness; its straddle checks will need their widths updated, which is the point of them. `Views/FindBar.swift`, possibly `Views/ContentView.swift`, possibly SPEC §6.5. Depends on (find-bar-narrow-column), which shipped.
