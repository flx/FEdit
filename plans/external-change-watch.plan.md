# external-change-watch

**Risk tier:** hi — a background-queue `DispatchSourceFileSystemObject` (and an FSEvents stream) feed `@MainActor` model mutation and an editor reload, with atomic-save fd re-arm and a last-writer race against (baked-in-autosave), which ships in parallel and shares the same `saveOpenFile()` write path. The failure modes are concurrency bugs — reload loops, missed events after an atomic rename, a self-write mistaken for an external change, or an external change silently clobbering unsaved edits — not simple UI plumbing.

## Goal

Reflect external edits to the open file automatically: watch the open file with a vnode `DispatchSource`, and when it changes on disk, reload a clean buffer into the editor preserving cursor/scroll, or — when the buffer has unsaved edits — keep the in-editor version and surface a subtle "changed on disk" indicator (no silent clobber, in either direction). Also watch each sidebar root recursively and re-scan on external add/remove so the tree stays current without manual Refresh. FEdit's own writes (Cmd+S, and (baked-in-autosave)'s debounced autosave, both funneled through `saveOpenFile()`) must never be mistaken for an external change.

## Acceptance criteria

Manually testable against an open text file and a sidebar root, with external mutations made from a terminal (`echo`, `printf >>`, `mv`, `rm`, `mkdir`, another editor's save) or by Claude editing the same file.

**Volume scope (T3, D5):** the promptness/timing criteria (1, 3, 4, 9–12) are specified for **local APFS/HFS+ volumes**. On network volumes (SMB/NFS) vnode/FSEvents delivery is unreliable, and on coarse-mtime filesystems (FAT/exFAT, and network shares) the `FileSignature` key is coarser — a same-size in-place external write landing within one mtime tick of FEdit's own write can collide and be missed. Both are accepted for v1: SPEC §11 is last-writer-wins with no cross-writer coordination.

Open-file reload (clean buffer):
1. With the buffer clean, an external edit to the open file appears in the editor within a fraction of a second (typical small files — the reload reads the whole file **synchronously on the main actor** up to `loadText`'s 100 MB cap, so a very large file takes proportionally longer; off-main read is out of scope, T2), with no manual switch. The caret stays at the same UTF-16 offset (clamped into the new length) and the scroll position is preserved (the first visible line is unchanged when the text above it is unchanged).
2. An external edit that truncates the file below the caret offset clamps the caret to the new end — no crash, no out-of-range selection.
3. **Atomic-rename re-arm:** an external *atomic* save (temp-file + `rename`, e.g. `mv new.txt open.txt` or another editor's save) is detected and reloaded, **and a second atomic save after the first is also detected** — proving the watcher re-armed onto the new inode rather than going deaf after the first rename.
4. An external *in-place* write (`printf 'x' >> open.txt`) is detected and reloaded (a `.write`/`.extend` event, no rename, no re-arm).
5. **External delete/recreate:** `rm`-ing the open file does not crash and does not blank the editor (the buffer is retained; SPEC §11 "save recreates it at the old path"). Recreating the file externally and editing it again is detected (the watcher re-establishes onto the recreated path).

Self-write suppression (the (baked-in-autosave) coordination):
6. **Cmd+S never self-reloads:** saving from the editor causes no reload, no flicker, and no "changed on disk" indicator. Rapid successive saves cause no reload storm. (Same must hold for (baked-in-autosave)'s debounced autosave once it ships — its writes go through the same `saveOpenFile()` and inherit this suppression.)
7. **Active-edit + autosave (post-(baked-in-autosave)):** typing continuously while autosave writes on its debounce produces no spurious "changed on disk" indicator and no reload — the disk (lagging the buffer) is recognized as self-written, not external.

Dirty-buffer conflict:
8. With unsaved edits, an external change does **not** overwrite the editor buffer (in-editor wins) and raises the "changed on disk" indicator (Tier 2). Saving then writes the buffer over the external version (last-writer = in-editor, SPEC §11) and clears the indicator. Switching files also clears it. **Near-cosmetic in the shipped config (T1):** with (baked-in-autosave) always-on, the ~0.75 s autosave flush writes the dirty buffer over disk (resolving in-editor's favor) and clears this indicator on its own, so the indicator is *reliably* observable only during **continuous typing** that keeps the buffer dirty across the external write — a paused dirty buffer is autosaved before the indicator can be seen. Qualify accordingly.

Sidebar tree (Tier 3):
9. Creating a file at the top level of an open root appears in the sidebar within ~1 s without manual Refresh; deleting one removes it.
10. Creating/deleting a file in a **subdirectory** of an open root is reflected (recursive watch), including a newly created subdirectory.
11. Removing a root from the sidebar stops watching it (a later change there triggers no rescan); adding a root starts watching it.
12. A burst of many external file creates coalesces into a single debounced rescan, not one rescan per file (no UI thrash).

## Tiers

### Tier 1 — Open-file vnode watcher, self-write suppression, clean-buffer reload

*Files:* new `FEdit/Models/FileWatcher.swift`, `FEdit/Models/WorkspaceModel.swift` (modify), `FEdit/Editor/CodeEditorView.swift` (modify).

**`FileWatcher.swift` — a single-file `DispatchSourceFileSystemObject` wrapper.**
- `final class FileWatcher: @unchecked Sendable`. All mutable *watcher* state (`source`, `fileDescriptor`, `watchedURL`, debounce `pendingFlush`, `needsRearm`) is confined to one private serial `DispatchQueue(label: "com.fedit.filewatcher")`; `watch`/`stop` called from the main actor immediately `queue.async` onto it, so there is a single serialization domain (`@unchecked Sendable` is justified by that confinement).
- **`var isActive: Bool` is a separate, main-owned flag — NOT a cross-queue read of the confined state (T4).** The dormant-check in `saveOpenFile` runs on the `@MainActor`, so it must not touch the queue-confined fields directly. Instead the wrapper mirrors its arm/disarm state into `isActive` **on a main-queue hop**: a successful `watch` sets it `true`, and `stop` / a re-arm that ultimately fails sets it `false`, each dispatched to `.main`. The main-actor reader thus observes only this main-owned Bool. (`@unchecked Sendable`'s confinement argument therefore covers exactly the queue-confined fields; `isActive` is excluded from it by construction.)
- `init(onChange: @escaping @Sendable () -> Void)`. The callback is invoked **on the main queue** (the wrapper does the hop), so the consumer runs where `@MainActor` model mutation is legal.
- `func watch(_ url: URL)`: stop any existing source, then `open(path, O_EVTONLY)` (no `O_NOFOLLOW` — follow a symlinked open file through to its target inode, matching `saveOpenFile()`'s `resolvingSymlinksInPath()` write target so watcher and writer track the same inode) and create `DispatchSource.makeFileSystemObjectSource(fileDescriptor:eventMask:queue:)` with mask `[.write, .extend, .delete, .rename, .revoke, .link]`. Store the resolved path.
- `func stop()`: cancel the source (its `cancelHandler` `close()`s the fd — the fd must be closed **only** in the cancel handler, never eagerly, or a re-used fd number races), clear state.
- **Event handling + debounce coalescing:** the source's `eventHandler` reads `source.data`; if it intersects `[.delete, .rename, .revoke]` it sets `needsRearm = true`; then it (re)schedules a single debounced flush ~150 ms out on the same queue (each event cancels and reschedules, so the delete+rename+write burst of one atomic save collapses to one flush).
- **Flush / re-arm:** on flush, if `needsRearm`, tear down the stale source+fd and re-`open` the watched path, **retrying on `ENOENT`** (up to ~5 attempts, ~50 ms apart) to ride out the brief window where a delete-then-create writer leaves the path momentarily absent (a true atomic `rename` never does, but non-atomic writers can). If the re-open ultimately fails, leave the watcher dormant (WorkspaceModel re-establishes it on the next `saveOpenFile()` / file open). Then invoke `onChange` on the main queue **once** per flush.

**`WorkspaceModel.swift` — own the watcher, suppress self-writes, reload clean buffers.**
- **`struct FileSignature: Equatable` is OWNED and introduced by THIS item** (in `FileWatcher.swift`): `{ inode: UInt64, size: Int64, mtimeSec: Int64, mtimeNsec: Int64 }` (mapping `st_ino` / `st_size` / `st_mtimespec`'s sec + nsec) with `static func of(_ url: URL) -> FileSignature?` via raw `stat(2)` on the resolved path. (baked-in-autosave provides **no** echo baseline — no `lastSavedText`, no signature; the entire suppression key and its capture live here.) This is the suppression key — cheap, and race-robust in a way a boolean "self-write in progress" flag is not (an atomic save fires several coalesced events, so a flag has no clean clear point; a signature is stateless).
- `private let fileWatcher = FileWatcher(onChange: …)` whose closure runs on the main queue and calls `MainActor.assumeIsolated { [weak self] in self?.fileDidChangeOnDisk() }` (same main-thread-assertion idiom as `WindowCloseGuardProxy`).
- `private var lastWriteSignature: FileSignature?` — the signature of the content FEdit itself last put on disk (or last loaded).
- `applyLoadedFile(url:text:)` (post-(baked-in-autosave): this method **already cancels the pending autosave** before replacing `openFile`, so a stale debounce timer never writes the newly loaded file) gains: `fileWatcher.watch(url)`, `lastWriteSignature = FileSignature.of(url)` (the freshly loaded content is the baseline — a change *after* load differs from it), and `openFileChangedOnDisk = false`. This covers both interactive `loadFile` and (session-restore)'s `silentlyLoadFile`, which already share it. **A reload does NOT route through `applyLoadedFile`** — this method (re)arms the watcher onto the URL, which is correct for an *open/switch* but wrong for a *reload* (the fd is unchanged); reloads use `reloadOpenFileFromDisk` instead (below).
- `saveOpenFile(alertOnFailure: Bool = true)` (the post-(baked-in-autosave) signature) gains, right after the atomic write on its **shared success branch**: `lastWriteSignature = FileSignature.of(resolvedURL)`, `openFileChangedOnDisk = false` (the write resolves any pending conflict in-editor's favor), and `fileWatcher.watch(openFile.url)` **only if `!fileWatcher.isActive`** (re-establishes after an external delete that was then re-created by this save; a no-op otherwise). The success branch is **shared** by Cmd+S, the switch/close/quit flush, and (baked-in-autosave)'s ~0.75 s debounced autosave — so **every** write, including each autosave, rebaselines the suppression key at one point. This single capture point is the whole suppression seam.
- `func fileDidChangeOnDisk()` (`@MainActor`), the flush consumer:
  1. `guard let openFile else { return }`.
  2. `guard let currentSig = FileSignature.of(resolvedURL) else { return }` — a failed `stat` means the file is currently gone (external delete, or mid-rename). Retain the buffer, do nothing (SPEC §11: a later save recreates it).
  3. `guard currentSig != lastWriteSignature else { return }` — **the self-write gate.** Equal ⇒ this is the content FEdit last wrote (or loaded); ignore. This is what makes Cmd+S / autosave silent (criteria 6–7), even while the buffer runs ahead of disk during active autosaved editing.
  4. `guard let diskText = try? loadText(from: url) else { return }` — transient read failure ⇒ skip; a later event retries. (Reuses the existing binary/size-cap guard, so a huge or now-binary external file is refused, not loaded.)
  5. `if diskText == openFile.text { lastWriteSignature = currentSig; openFileChangedOnDisk = false; return }` — content is byte-identical to the buffer (e.g. an external touch, or an external write of what we already have); rebaseline and do nothing. (This is a redundant-reload guard, **not** a defense against a missed self-write — it sits *after* the step-3 signature return, so it can only suppress a needless reload, never recover a change the signature gate already let through; see the coarse-mtime limitation in the load-bearing assumptions.)
  6. **Real external change.** If `!openFile.isDirty` → `reloadOpenFileFromDisk(text: diskText, signature: currentSig)` (the dedicated reload path below). Otherwise (dirty) → in-editor wins: leave `openFile` untouched, set `openFileChangedOnDisk = true`, and set `lastWriteSignature = currentSig` (so the same external state does not re-fire the indicator on the next coalesced event).
- `func reloadOpenFileFromDisk(text: String, signature: FileSignature)` (`@MainActor`) — the clean-buffer reload path. It deliberately does **not** route through `applyLoadedFile` (which would re-arm the watcher onto an unchanged fd). Steps, in order:
  1. `cancelPendingAutosave()` **at the top**, before touching `openFile`, so no straggler autosave work item survives the reload and later writes stale pre-reload text over the just-loaded content. *(Requires (baked-in-autosave) to expose `cancelPendingAutosave()` — see the seam contract; this is a hard requirement, not defense-in-depth.)*
  2. Capture the caret (UTF-16 offset) and first-visible character index — actually captured inside `CodeEditorView`'s programmatic branch (below); the model just replaces the buffer.
  3. Replace `openFile` directly: `openFile = OpenFile(url: openFile.url, text: text, isDirty: false)` — a clean buffer, `documentID` (the URL) unchanged so the editor takes the external-change branch, not the file-switch branch.
  4. `lastWriteSignature = signature` (the just-read on-disk signature becomes the new baseline) and `openFileChangedOnDisk = false`.
  The caret/scroll restore itself happens in `CodeEditorView.updateNSView`'s `else if textView.string != text` branch (below), driven by this `openFile.text` swap.
- `@Published var openFileChangedOnDisk = false` — set only in the dirty branch of `fileDidChangeOnDisk`; cleared by `applyLoadedFile` (switch), by `reloadOpenFileFromDisk` (clean reload), and by `saveOpenFile`'s shared success branch (the save resolves the conflict, in-editor's favor). Consumed by Tier 2; inert until then.

**`CodeEditorView.swift` — make the existing external-change branch preserve scroll.**
- The dormant `else if textView.string != text` branch (currently caret-clamp only, documented "no shipped item drives this branch yet") becomes the reload applier: a model reload replaces `openFile.text` with `documentID` unchanged, so `updateNSView` takes this branch. Enhance it to also preserve scroll by reusing (editor-font-zoom)'s proven helpers: capture `let anchorChar = coordinator.firstVisibleCharIndex(textView)` *before* the string swap, and after restoring the clamped caret call `coordinator.scrollCharToTop(textView, characterIndex: anchorChar)`. **Report the clamped caret (N1):** after computing the clamped location, fire `onCursorChange?(clamped)` (deferred one runloop pass, matching the file-switch branch, since the callback writes @State) — otherwise a *truncating* reload leaves (session-restore)'s `cursorLocation` holding the pre-reload offset, which can be past the new end and would persist an out-of-range value in the next snapshot. The branch stays wrapped in `isProgrammaticUpdate = true` (so the swap never round-trips through `textDidChange` to mark the buffer dirty — load-bearing: a reload must leave a clean buffer clean) and keeps its `pendingHighlight?.cancel()` + synchronous `highlightNow` (already present).

*Buildable/revertible:* the open file tracks external edits (clean reload with cursor/scroll preserved), Cmd+S is silent, atomic-save re-arm works, a dirty buffer is never clobbered (the indicator flag is set but not yet shown). Reverting the tier restores manual-only refresh (SPEC §5.2 original). No dependency on Tier 2/3.

### Tier 2 — "Changed on disk" indicator

*Files:* `FEdit/Views/ContentView.swift` (modify).

- Surface `workspace.openFileChangedOnDisk` in the window subtitle (the minimal surface — no new view API). The subtitle already carries the dirty marker; extend it so a dirty conflict reads **"Edited — changed on disk"**, a clean state stays `""`, and dirty-without-conflict stays `"Edited"`. Concretely, replace the `.navigationSubtitle(…)` expression with a small computed string over `(isDirty, openFileChangedOnDisk)`.
- Scope decision: a subtitle string is the whole indicator for v1. A dedicated editor-header badge or a "reload"/"keep mine" affordance is deliberately **out of scope** — with (baked-in-autosave) the dirty conflict window is tiny (autosave promptly writes the buffer, resolving in-editor's favor and clearing the flag), so a heavier affordance would rarely be seen.

*Buildable/revertible:* criterion 8's visible half. Reverting loses only the indicator; the no-clobber behavior (Tier 1) is unaffected.

### Tier 3 — Recursive sidebar-root watch → debounced re-scan

*Files:* new `FEdit/Models/DirectoryTreeWatcher.swift`, `FEdit/Models/WorkspaceModel.swift` (modify).

- **Mechanism choice — FSEvents, not vnode.** A vnode `DispatchSource` watches a single fd (one directory), and a non-recursive root watch would miss the common motivating case (Claude creating files in *subdirectories*). Recursive vnode coverage is infeasible — one open fd per directory across the whole tree exhausts `RLIMIT_NOFILE` on a large repo. FSEvents is macOS's purpose-built cheap recursive path watcher: one kernel stream per root, latency-batched. Unsandboxed (SPEC §2), plain paths need no entitlement. So the open **file** stays on the precise/immediate vnode watcher (Tier 1); the **tree** uses FSEvents.
- `DirectoryTreeWatcher.swift`: `final class DirectoryTreeWatcher: @unchecked Sendable` wrapping `FSEventStreamCreate` with flags `[.useCFTypes, .fileEvents]`, scheduled on a private serial dispatch queue (`FSEventStreamSetDispatchQueue`). `init(onChange: @escaping @Sendable ([String]) -> Void)` — **the callback carries the batch of changed paths** (from the FSEvents `eventPaths` argument), so the consumer can gate on them (below); it is delivered on the main queue. `func watch(roots: [URL])` (re)creates the stream for the given paths with a built-in latency (~0.3 s) that FSEvents itself uses to coalesce bursts (criterion 12), and **passes `sinceWhen = kFSEventStreamEventIdSinceNow` (N2)** so a fresh `watch(roots:)` — including the one `addFolders` issues during (session-restore) — does not replay the volume's historical events (which would trigger a spurious full rescan on every launch). `func stop()`. The C callback trampolines through the `info` pointer to `onChange`.
- **Tree-level self-write / noise skip gate (D3).** FSEvents has no built-in self-write suppression, and under (baked-in-autosave) the open file is rewritten every ~0.75 s while typing, while (git-changed-badge) shells out to `git` (which writes under `.git`) on save/activation — so an ungated stream would fire `refreshAll()` (a full recursive main-thread rescan + whole-sidebar re-diff) on FEdit's own routine writes. The `WorkspaceModel` main-queue closure therefore filters the batch **before** rescanning:
  - Drop the open file's own path (`openFile?.url.resolvingSymlinksInPath().path`) — an autosave/Cmd+S write to the open file changes no tree *structure*, and content is already handled by the Tier 1 vnode watcher.
  - Drop any path that falls inside the scanner skip-set — `.git`, `node_modules`, `.build`, `DerivedData`, and any dotfile/hidden path — **mirroring `FileNode.skippedDirectoryNames` + `.skipsHiddenFiles`** so the watcher's notion of "interesting" matches exactly what a rescan would surface. (This is what makes git-changed-badge's `.git` writes and build-tool churn free.)
  - If **every** path in the batch was dropped, return without rescanning.
- `WorkspaceModel`: `private let treeWatcher = DirectoryTreeWatcher(onChange: …)` whose main-queue closure runs the skip gate above inside `MainActor.assumeIsolated { [weak self] in … }` and, only if a non-skipped path survives, calls `self?.refreshAll()`. **`refreshAll()` republishes `roots` only when the freshly rescanned structure actually differs from the current tree** (compare the rescanned node structure against the published `roots`; if identical, assign nothing) — so a surviving-but-structure-neutral event (e.g. an in-place content write to an unopened file) does not thrash the sidebar or re-fire (session-restore)'s snapshot `.onChange`. Re-point via `treeWatcher.watch(roots: roots.map(\.url))` from `addFolders` and `removeRoot` (the only two sites where the *set* of roots changes). `refreshAll()` re-scans in place without changing the root URL set, so the watcher needs no re-point there — and re-pointing to the same paths generates no FS event, so a watcher-driven `refreshAll` cannot feed back into itself.

*Buildable/revertible:* criteria 9–12. Reverting loses auto tree refresh only; manual Refresh (unchanged) remains.

## Interface between tiers

`WorkspaceModel` surface, frozen per tier:
- Tier 1 → 2/3: `@Published var openFileChangedOnDisk: Bool`; `struct FileSignature` (owned here); `private var lastWriteSignature`; `private let fileWatcher`; `func fileDidChangeOnDisk()`; `func reloadOpenFileFromDisk(text:signature:)` (calls `cancelPendingAutosave()` at the top); the augmented `applyLoadedFile` and `saveOpenFile(alertOnFailure:)` shared success branch. `FileWatcher` public API: `init(onChange:)`, `watch(_:)`, `stop()`, `var isActive` (the **main-owned** dormant-check flag, updated on a main-queue hop — T4; read by `saveOpenFile` on the `@MainActor`).
- Tier 2 consumes only `openFileChangedOnDisk`; adds no model API.
- Tier 3 → : `private let treeWatcher`; `DirectoryTreeWatcher` public API `init(onChange: ([String]) -> Void)` (the callback carries the changed-path batch for the skip gate), `watch(roots:)` (uses `kFSEventStreamEventIdSinceNow`), `stop()`. Adds no cross-tier surface beyond the re-point calls in `addFolders`/`removeRoot`.

## Required seam from (baked-in-autosave)  ← cross-plan contract

(baked-in-autosave) ships **first**, is reconciled to the same contract in parallel, and shares `WorkspaceModel.saveOpenFile(alertOnFailure:)`. The seam is split cleanly: **baked-in-autosave provides three guarantees; THIS item adds the `FileSignature` echo baseline on top of them.** baked-in-autosave provides **no** `lastSavedText` and no echo baseline — the entire suppression key is owned here.

**baked-in-autosave guarantees (all REQUIRED):**

a. **Single write path.** Every disk write to the open file — the ~0.75 s autosave debounce, and the on-switch / focus-loss / close / quit flushes — funnels through `WorkspaceModel.saveOpenFile(alertOnFailure:)`. No second, lower-level write path bypasses it. This is what lets one `lastWriteSignature` capture on that method's shared success branch cover every write, including autosave. (If baked-in-autosave ever added a shared lower-level primitive underneath `saveOpenFile`, the signature capture would move down with it — but the contract is that `saveOpenFile` stays the single write path.)

b. **Work item reads text at fire time and re-checks `isDirty`.** The debounced autosave work item reads `openFile.text` when it *fires* (not when it is *scheduled*) and re-checks `openFile?.isDirty == true` at fire time. So a clean-buffer reload that replaced `openFile` between schedule and fire makes any surviving item either bail (buffer now clean) or write the already-reloaded content (a harmless no-op that re-matches `lastWriteSignature`) — never resurrect pre-reload text over an external change.

c. **Exposes `func cancelPendingAutosave()` (REQUIRED).** This plan calls it at the **top** of `reloadOpenFileFromDisk`, before replacing `openFile`, so no autosave work item lingers across a reload. This is a hard requirement, not defense-in-depth: `reloadOpenFileFromDisk` bypasses `applyLoadedFile` (which is where baked-in-autosave's own cancellation lives), so without an explicit `cancelPendingAutosave()` a straggler debounce could fire after the reload.

**THIS item adds:** `struct FileSignature` + `FileSignature.of(_:)`; the `lastWriteSignature = FileSignature.of(resolvedURL)` capture on `saveOpenFile`'s shared success branch (so every write, autosave included, rebaselines the key) and in `applyLoadedFile`; the self-write gate in `fileDidChangeOnDisk`; and the `cancelPendingAutosave()` call at the top of `reloadOpenFileFromDisk`.

**Also folded in from baked-in-autosave (this plan is anchored on the post-autosave model, D4):** baked-in-autosave **deletes** (open-save)'s four-button Save/Always Autosave/Don't Save/Cancel dialog, the `autosaveOnFileSwitch` toggle, and `SettingsKey.autosaveOnFileSwitch`; `resolveDirtyFile()` becomes a silent flush (`saveOpenFile() ? .proceed : .cancel`); `applyLoadedFile` already cancels the pending autosave. This plan references none of the deleted machinery.

The last-writer race resolves cleanly under this contract, in every ordering: dirty buffer + external write → in-editor wins (watcher sets the indicator, autosave later writes the buffer over disk); clean buffer + external write → external wins (reload); an interleaved autosave is always recognized as a self-write via the signature and never mistaken for the external change.

## Load-bearing assumptions

1. **The editor's external-change branch exists and is a pure applier.** `CodeEditorView.updateNSView`'s `else if textView.string != text` branch (editor-core, currently unexercised) swaps text under `isProgrammaticUpdate`, so a model-driven reload with unchanged `documentID` replaces the buffer without marking it dirty and without an undo reset. If that branch were removed, a reload would need a new editor seam.
2. **All disk writes funnel through `saveOpenFile(alertOnFailure:)`.** Post-(baked-in-autosave) this stays the single write path — Cmd+S, the switch/close/quit flush, and the autosave debounce all route through it (baked-in-autosave guarantees no bypassing lower-level write). The suppression seam rests on this: the one `lastWriteSignature` capture on its shared success branch covers every write.
3. **`WorkspaceModel` is `@MainActor`.** Background `DispatchSource`/FSEvents events must hop to the main queue before mutating it; the wrappers own that hop.
4. **`FileSignature` is only reliably collision-free on high-resolution-mtime local volumes (APFS/HFS+).** APFS records nanosecond `st_mtimespec`, so on a local volume two distinct writes never collide on `FileSignature` and the self-write gate cannot mistake an external write for a self-write. **Accepted v1 limitation (D5):** on coarse-mtime volumes (SMB/NFS/FAT/exFAT, ~1–2 s mtime granularity) a **same-size in-place external write landing within one mtime tick of FEdit's own write** produces an identical `(inode, size, mtime)` signature and is missed (the step-3 gate reads it as an echo). This is not defended against — the step-5 `diskText == openFile.text` check sits *after* the gate and can only suppress a needless reload, never recover a change the gate already dropped. It is accepted because SPEC §11 is last-writer-wins with no cross-writer coordination, and the timing criteria are scoped to local volumes.
5. **Atomic save unlinks the watched inode.** FEdit's own `Data.write(options: .atomic)` and external atomic savers replace the file via temp + `rename`, so the vnode fires `.delete`/`.rename` and the fd must be re-armed by re-opening the path — this is the norm, not an edge case.
6. **Unsandboxed (SPEC §2):** `O_EVTONLY` opens, raw `stat`, and `FSEventStreamCreate` on plain paths need no security-scoped access or entitlement.
7. **A tiny self-write→signature-capture race is accepted.** Between `saveOpenFile()`'s atomic write and its `stat` for `lastWriteSignature`, an external write could (microseconds) land and be captured as the baseline, causing that one external change to be missed. With (baked-in-autosave) making the dirty window tiny and the window itself being back-to-back main-actor calls, this is accepted for v1 (SPEC §11 is already last-writer-wins with no coordination).

## Out of scope

- A reload/merge/diff affordance or "keep mine vs take theirs" UI — the indicator is a subtitle string only; last-writer-wins per SPEC §11.
- Watching files **not** currently open (only the one open file gets a vnode watcher; the tree watcher covers existence/structure, not content of unopened files).
- Off-main reading/decoding of the reloaded file — kept on the main actor, bounded by `loadText`'s existing 100 MB cap, per SPEC §11's "synchronous is acceptable for v1".
- Multi-window coordination on the same file — each window's watcher acts independently; still last-writer-wins (SPEC §11).
- Preserving caret by content anchoring across large external rewrites — the caret is preserved by clamped UTF-16 offset (the existing branch's behavior), which is approximate by design.
- Git-status refresh on watcher events — that wiring belongs to (git-changed-badge), which lists this item as one of its refresh triggers.

## Recorded decisions

- **Signature over boolean flag** for self-write suppression: an atomic save emits several coalesced events with no clean point to clear a flag; a stateless `(inode, size, mtime)` signature compared per flush is race-robust. (Tier 1.)
- **FSEvents (recursive) for the tree, vnode for the file:** vnode can't recurse without one-fd-per-directory fd exhaustion; FSEvents is the cheap recursive path watcher; the open file wants the precise, immediate vnode source. (Tier 3.)
- **Indicator is a subtitle string, minimal by intent:** with (baked-in-autosave) the dirty-conflict window is tiny, so a heavier affordance would rarely surface. (Tier 2.)
- **Reload preserves cursor (clamped offset) + scroll (first-visible-line anchor)** by reusing (editor-font-zoom)'s `firstVisibleCharIndex`/`scrollCharToTop`, not new machinery. (Tier 1.)
- **Tree watcher gates FSEvents before rescanning:** FSEvents has no self-write suppression, so the batch is filtered (drop the open file's own path + the scanner skip-set: `.git`, `node_modules`, `.build`, `DerivedData`, dotfiles) and `refreshAll` republishes `roots` only on a real structural diff — otherwise (baked-in-autosave)'s ~0.75 s autosave writes and (git-changed-badge)'s `.git` writes would drive a full recursive main-thread rescan on FEdit's own routine activity. (Tier 3.)
- **`FileSignature` collision-free only on local high-res-mtime volumes (APFS/HFS+):** a same-size in-place external write within one mtime tick of FEdit's own write can be missed on coarse-mtime/network volumes; accepted per SPEC §11 (last-writer-wins), timing criteria scoped to local volumes. (Tier 1.)
