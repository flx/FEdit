- [ ] (find-bar-gutter-inset) The find bar's query field is inset from the editor **column's** edge instead of from the text pane, so it hangs left over the line-number gutter and sits out of line with the file name directly above it — reported 2026-08-22 with a screenshot: `plans/find-bar-gutter-inset-repro.png`. Cause is exact, read off HEAD, no probe needed: `ContentView.editorColumn` gives the header strip `ColumnHeaderBar(title: name, leadingInset: editorGutterWidth)` and `ColumnHeaderBar` adds the standard 8 pt *on top of* that inset (`Views/ColumnHeaderBar.swift`), so the file name's content edge lands at `gutterWidth + 8` — but the `FindBar` rendered immediately below it in the same `VStack` carries only `.padding(.horizontal, 8)` (`Views/FindBar.swift`, modifiers at the end of `body`) and never receives `editorGutterWidth` at all, so its content edge lands at 8 pt, i.e. a full `gutterWidth` too far left, squarely over the gutter. The screenshot's measurements agree: the field's left edge is ~8 pt from the column edge while `DESIGN.md` above it is ~35 pt, and `updateThickness` for that 3-digit document gives `ceil(3 × 10 pt-monospaced digit) + 4 × 2` ≈ 26–27 pt of gutter — 27 + 8 = 35. Fix shape: thread the same `editorGutterWidth` into `FindBar` as a `leadingInset` property and add it to the leading padding, mirroring `ColumnHeaderBar`'s documented contract, so the bar's controls align with both the title above and the text below. Two things the plan must settle rather than assume: (1) whether the bar's **background** should also start past the gutter or keep spanning the full column width — it carries the same hairline the header strips do and reads as chrome, so spanning is probably right and only the content should indent; (2) the inset is **live** — `onGutterWidthChange` fires on digit-count boundaries and on font zoom, and it arrives through a `DispatchQueue.main.async` hop in `CodeEditorView.makeNSView`, so the field must not visibly jump or animate when the gutter grows while the bar is open. Cosmetic only; no behavior change, no SPEC change (§6.5 describes the bar's controls, not its metrics). `Views/FindBar.swift`, `Views/ContentView.swift`. Depends on (editor-find), which shipped. Touches no file (gutter-top-overflow) touches — the two can be batched in parallel.
- [ ] (gutter-top-overflow) The line-number gutter draws the topmost partially-scrolled line's number above the editor's top edge, where there is no text row to match it — reported 2026-08-22 with a screenshot: `plans/gutter-top-overflow-repro.png` (scrolled so line 137 is only slivered at the top, its `137` is painted straddling the boundary the editor shares with the chrome above it, i.e. across `ColumnHeaderBar`'s bottom hairline). With the find bar open the same number straddles the find bar's hairline instead — visible at the top of `plans/find-bar-gutter-inset-repro.png`, where `137` is half-clipped with nothing beside it. **Read off `Editor/LineNumberRulerView.swift:129-187`; NOT probe-confirmed — the first tier of the plan must reproduce and pixel-measure before choosing a fix.** `drawHashMarksAndLabels` starts its walk at `LogicalLine.lineStart(in: nsString, containing: visibleCharRange.location)`, i.e. at the logical line containing the first visible *character*, so the topmost line drawn is by construction one whose fragment begins above `visibleRect.minY`; the loop then carries a break for fragments past the bottom (`if fragmentRectInTextView.minY > visibleRect.maxY { break }`) and **no counterpart guard on the top side**, and `draw(lineNumber:in:)` centers the glyph in the **full** fragment rect (`y = fragmentRect.minY + (fragmentRect.height - size.height) / 2`) regardless of how much of that fragment is actually on screen — so when only a line's bottom sliver is visible, its number is placed above the visible band. Two candidate mechanisms the plan must separate, because they take different fixes and the wrong one is a regression: (a) the number is merely flush against the extreme top edge and is being clipped, which is what Xcode does too — then the fix is cosmetic (clamp the drawn `y` into the visible band, or skip a fragment less than ~half visible) and must be justified against the fact that a partially clipped top number is normal editor behavior; (b) the ruler genuinely paints **outside** the scroll view's content area, in which case the fix is clipping/geometry on the `NSRulerView` side, not the drawing loop. Measure the repro against `LayoutMetrics.columnHeaderHeight = 28` to tell them apart. Related-by-boundary, not by cause: the gutter deliberately has no vertical separator line (documented in `drawHashMarksAndLabels` — its top met the header strip and read as a hairline running up through the title), so this is the second cosmetic collision at that same top boundary; keep the two consistent. `Editor/LineNumberRulerView.swift`, possibly `Editor/CodeEditorView.swift` if the fix is ruler geometry, SPEC §6.2. No dependencies. Touches no file (find-bar-gutter-inset) touches — the two can be batched in parallel.
