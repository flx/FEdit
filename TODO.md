- [ ] (gutter-top-overflow) The line-number gutter draws the topmost partially-scrolled line's number above the editor's top edge, where there is no text row to match it — reported 2026-08-22 with a screenshot: `plans/gutter-top-overflow-repro.png` (scrolled so line 137 is only slivered at the top, its `137` is painted straddling the boundary the editor shares with the chrome above it, i.e. across `ColumnHeaderBar`'s bottom hairline). With the find bar open the same number straddles the find bar's hairline instead — visible at the top of `plans/find-bar-gutter-inset-repro.png`, where `137` is half-clipped with nothing beside it. **Read off `Editor/LineNumberRulerView.swift:129-187`; NOT probe-confirmed — the first tier of the plan must reproduce and pixel-measure before choosing a fix.** `drawHashMarksAndLabels` starts its walk at `LogicalLine.lineStart(in: nsString, containing: visibleCharRange.location)`, i.e. at the logical line containing the first visible *character*, so the topmost line drawn is by construction one whose fragment begins above `visibleRect.minY`; the loop then carries a break for fragments past the bottom (`if fragmentRectInTextView.minY > visibleRect.maxY { break }`) and **no counterpart guard on the top side**, and `draw(lineNumber:in:)` centers the glyph in the **full** fragment rect (`y = fragmentRect.minY + (fragmentRect.height - size.height) / 2`) regardless of how much of that fragment is actually on screen — so when only a line's bottom sliver is visible, its number is placed above the visible band. Two candidate mechanisms the plan must separate, because they take different fixes and the wrong one is a regression: (a) the number is merely flush against the extreme top edge and is being clipped, which is what Xcode does too — then the fix is cosmetic (clamp the drawn `y` into the visible band, or skip a fragment less than ~half visible) and must be justified against the fact that a partially clipped top number is normal editor behavior; (b) the ruler genuinely paints **outside** the scroll view's content area, in which case the fix is clipping/geometry on the `NSRulerView` side, not the drawing loop. Measure the repro against `LayoutMetrics.columnHeaderHeight = 28` to tell them apart. Related-by-boundary, not by cause: the gutter deliberately has no vertical separator line (documented in `drawHashMarksAndLabels` — its top met the header strip and read as a hairline running up through the title), so this is the second cosmetic collision at that same top boundary; keep the two consistent. `Editor/LineNumberRulerView.swift`, possibly `Editor/CodeEditorView.swift` if the fix is ruler geometry, SPEC §6.2.
