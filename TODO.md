- [ ] (preview-bold-spans) `**bold**` is silently not bold — and the *wrong* run is bolded instead — reported 2026-08-21 with a screenshot. Two independent root causes, both probe-confirmed against HEAD; full traces, controls, and the working baseline that must not regress: `plans/preview-bold-repro.md`. **(1) The reported case:** `MarkdownBlockParser.parse` has no **list-item continuation** — a wrapped list item's second line matches none of steps 1–7 and falls to step 8, paragraph continuation (`Preview/MarkdownRenderer.swift:183-190`), starting a *new block*. A `**…**` span wrapped across those lines is therefore split across two blocks; the inline parser runs per block, so each half holds an unpaired `**` that emits literally, and the orphaned closing `**` becomes an **opener** that pairs with the next `**` further down the document — bolding a long arbitrary run. Controls confirm the diagnosis: the identical span on one line in a list item is bold, and the identical wrap in a plain paragraph is bold (paragraph lines merge with a space; list continuations do not). Same gap also leaks the continuation line's leading indent into the text and can double-space the join. **(2) Independent:** `MarkdownInlineParser` commits to the **nearest** closer with no backtracking and no CommonMark left/right-flanking delimiter-run rule, so a single stray `*` earlier in the same block re-pairs every asterisk after it — `2 * 3 and **bold** here` renders "bold" as *italic* with a leftover `*`, and an odd/even count of strays decides whether the rest of the paragraph re-syncs. That rule is documented as deliberate in the parser's header comment, so fixing it is a **design change with a recorded reversal**, not a patch — the plan must decide how much of CommonMark's delimiter-run rule to adopt and re-word that comment. SPEC §8.2 promises `**bold**`, so no non-goal moves; add the continuation behavior to §8.2's paragraph/list bullets. Both causes must land with harness cases in `scripts/MarkdownRendererTests` (block-split *and* delimiter-pairing), and the fix must keep `MarkdownAnchor`'s strictly-ascending invariant — merging continuation lines into the list item removes an anchor, which `MarkdownRenderer.assertStrictlyAscending` and the §8.3 scroll-sync binary search both read. Adjacent gap seen in the same screenshot, deliberately **not** in scope: `- [ ]` task-list checkboxes render as a bullet plus literal `[ ]`. `Preview/MarkdownRenderer.swift`, `scripts/MarkdownRendererTests`, SPEC §8.2. No dependencies. **Ships before (preview-tables)** — same file, same `parse` classification loop; do not batch the two in parallel.
- [ ] (preview-tables) GFM tables render as one run-on paragraph in the preview — reported 2026-08-21 with a screenshot; source, observed output, and root-cause trace: `plans/preview-tables-repro.md`, screenshot `plans/preview-tables-repro.png`. A 5-column pipe table comes out as a single wrapped paragraph with every row space-joined, so even the source's line structure is lost. Root cause is exact, not a glitch: `MarkdownBlock` has no `.table` case, so every `|…|` row falls through classification steps 1–7 to step 8, paragraph continuation, which appends it to the accumulator flushed with `joined(separator: " ")` (`Preview/MarkdownRenderer.swift:183-190`); the `| --- | --- |` delimiter row is not a horizontal rule either (`isRule` sees the leading `|`), so nothing even breaks the block, and adjacent prose is swallowed too. Fix: recognize a GFM pipe table (header row + delimiter row) as a new `MarkdownBlock.table` case and render it as an aligned grid — `NSTextTable`/`NSTextTableBlock` is the native TextKit 1 route, monospaced fixed-width padding is the cheap fallback; pick in the plan and say why. **Reverses a SPEC §8.2 non-goal** ("Not in v1: tables, …") — §8.2 must be edited to admit tables and state the exact subset supported (leading/trailing pipes optional? `:---:` alignment honored or ignored? inline spans inside cells?). Hard constraints: the reporter's own table is **ragged** — the last row has 4 pipes where the header has 6 — so the parser must degrade gracefully (pad/truncate rows to the header's column count) rather than require well-formed input, and a `|` line that is *not* preceded by a delimiter row must keep rendering as today's paragraph text. The table must emit exactly **one** `MarkdownAnchor` at its first row: `MarkdownRenderer.assertStrictlyAscending` requires strictly ascending `(sourceLine, location)` and §8.3's scroll sync binary-searches them. `Preview/MarkdownRenderer.swift`, `Preview/MarkdownPreviewView.swift` (only if the grid needs container/width handling), `scripts/MarkdownRendererTests`, SPEC §8.2, README. Depends on (preview-bold-spans) only for file ordering — same file, do not batch in parallel.
